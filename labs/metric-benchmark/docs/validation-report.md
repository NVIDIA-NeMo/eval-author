# Validation report

The validation tool checks that saved execution results satisfy the
[results format and constraints](results-format.md#constraints) before score
analysis.

It reads the results index and raw execution evidence, verifies that
every configured agent/task pair is accounted for, and checks that the recorded
outcomes agree with the native evidence and prepared inputs. When those checks
pass, it produces the report described here.

## Generating the report

From the repository root, invoke the validation CLI with:

```bash
uv run python labs/metric-benchmark/validate_results.py \
  --benchmark experiment.yml \
  --results-root experiment-results \
  --output validation.json
```

Supply these required arguments:

- `--benchmark`: path to the experiment YAML file and its references to prepared inputs.
- `--results-root`: whole experiment output directory containing `execution.json` and the case results directories.
- `--output`: path for the validation report, outside the results root; `validation.json` is an example filename.

By default, the tool validates every configured case. Add `--case case-id` to
validate only that case example, using the same `--results-root` path. The
experiment’s `execution.json` maps each case ID to its results index.

Optionally, add `--allow-unsigned` when input SHA pins are missing during iteration;
any supplied pins are still verified.

The CLI checks all selected cases and writes one report only if every selected
case passes. A filtered invocation uses the same report structure with one case.
Explicitly unavailable observations do not themselves cause validation to fail. If any constraint fails, the command exits nonzero and
no new report is written. An existing output file can be reused only if its
contents are identical; choose a new output path for changed results.

The [Python library](tools.md#validate-a-results-directory) returns the same report
as a dictionary.

## Report format: `validation.json`

| Field | Meaning | Source |
| --- | --- | --- |
| `run_id` | Execution identity shared by the selected cases. | `execution.json` → `run_id`, originally the runner’s `--run-id`. |
| `cases` | Map from each validated case ID to its report below. | Configured case IDs, optionally filtered by CLI `--case`. |

Each entry in `cases` contains:

| Field | Meaning | Source |
| --- | --- | --- |
| `case_id` | Selected prepared case. | YAML: `experiment.yml` → `cases[].case_id`, optionally selected by the validator’s `--case` flag. |
| `run_id` | Execution identity copied from the index. | Copied from `results.json` → `run_id`, originally supplied by the execution CLI’s `--run-id`. |
| `expected_pairs` | Number of configured agents multiplied by number of tasks. | Validator-generated from the selected case’s `agent.yml` and `tasks.yml` manifests. |
| `observations` | Number of execution entries, including missing entries and retries. | Validator-generated count of `results.json` → `execution_results`. |
| `unavailable` | Entries with null configured measurements, each containing `agent`, `task`, `attempt`, and `reason`. | Validator-generated from execution entries whose configured metric value is `null`. |
| `files` | Map of relative evidence-file paths to `sha256:<hex>` digests. | Validator-generated by hashing files under that case’s results directory. |

Each case’s file manifest covers ordinary files under its results directory
except its `results.json`. Paths in `files` are relative to that case directory.
Consumers hash the index separately; an execution backend may validate an
in-memory index before publishing that file. The report
therefore is not a self-contained seal of the index. Placing it outside the root
also prevents it from becoming part of its own evidence manifest.

These checks establish consistency with the prepared inputs, not the scientific
validity of the results or whether all trials came from one submission.

## Example validation output

The checked-in [validation.json](../../../tests/fixtures/metric_benchmark_results/validation.json)
is the expected report for the [mock results directory](results-format.md#mock-results).
With the case’s `files` digest map omitted here for brevity, it contains:

```json
{
  "run_id": "mock-run-001",
  "cases": {
    "rho-agent": {
      "case_id": "rho-agent",
      "run_id": "mock-run-001",
      "expected_pairs": 9,
      "observations": 9,
      "unavailable": []
    }
  }
}
```

The nine observations account for one baseline and two mutants across three tasks.
`unavailable` is empty because every configured measurement is present, including
the mutants’ zero rewards. The full `files` map contains 18 evidence-file hashes:
one native trial record and one verifier reward file for each observation.
The report sits beside `experiment-results/`, outside the experiment output root.
Validating this one-case fixture with or without `--case rho-agent` yields the same report.
